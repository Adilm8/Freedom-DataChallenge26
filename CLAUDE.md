## Контекст проекта

Прототип Conversation Quality Analytics для Freedom Broker. Система оценивает работу оператора в чате или звонке по настраиваемому чек-листу, показывает баллы с обоснованием и репликой-доказательством, поддерживает апелляцию и пересмотр оценки.

- Главный критерий отбора — **точность AI-оценки** против эталона (Ground Truth) на 10 новых транскриптах. Дальше: функциональность, UX, честность процесса (реальный анализ, а не заготовки), разнообразие подходов. Полный текст — `docs/task/selection_criteria.md`.
- Чек-лист: 8 критериев, веса 10/15/20/20/15/15/5, критерий 08 — флаг без баллов. N/A перераспределяет вес. Итог округляется до 2 знаков. Источник истины — `docs/CQA_Chat_Quality_Checklist.pdf`; текстовая копия со шкалами, памяткой и примером расчёта — `docs/checklist.md` (давай подагентам её, а не PDF).
- Задание (функции, формат данных, сдача) — `docs/task/brief.md`.
- Данные: API организаторов, `GET ...&group_id=DEV`. 65 диалогов (чаты RU 30 / KZ 15 / EN 15 + 5 звонков RU `p4-ru-*`), роли `client/operator/bot/system`, время у чатов `MM:SS`, у звонков ISO 8601. Для контроля поменяется только `group_id`. Снапшот — `data/raw/DEV.json` (в git не коммитится).
- Через 23 часа после старта: контрольные транскрипты + замена одного критерия через UI. Через 24 часа: стоп-код, открытый Git, README.

## Окружение

- Python 3.11: `uv venv -p 3.11 .venv && source .venv/bin/activate && uv pip install -r requirements.txt`.
- Настройки и ключи — только `.env` (шаблон `.env.example`). URL API организаторов с подписью `sig` — тоже секрет, живёт только в `.env`. Гайд организаторов (PDF) содержит этот URL — в репозиторий его не класть.
- Данные: `python scripts/fetch_dataset.py` (из API) или `python scripts/fetch_dataset.py --from-file <Data.txt>` (без сети).
- Запуск: `uvicorn backend.app.main:app --reload` → http://localhost:8000. Тесты: `pytest -q`.
- Облачные сессии: используй среду `Freedom-DataChallenge26` (открыты `openrouter.ai` и хост API организаторов, зависимости ставятся при старте). В Default-среде эти хосты закрыты — работай от снапшота.

## LLM внутри решения

Это про модели, которые оценивают диалоги в продукте, а не про подагентов Claude Code.

- Провайдеры за интерфейсом `LLMProvider`, все через OpenAI-совместимый API и SDK `openai`:
  - `openrouter` — основной (`OPENROUTER_API_KEY`, base URL `https://openrouter.ai/api/v1`). Модель — `OPENROUTER_MODEL` в `.env`; доступны Claude, GPT, Gemini и открытые модели.
  - `gemini` — бесплатный ключ Google AI Studio (`GEMINI_API_KEY`, OpenAI-совместимый endpoint). Для черновых прогонов и разметки; у бесплатного тарифа лимиты RPM/RPD, данные могут использоваться Google — **реальные звонки `p4-ru-*` туда не отправлять**.
  - `ollama` — локальная модель, позже и только если останется время (критерий «разнообразие подходов»).
- Бюджет OpenRouter ограничен. Дорогие модели — только для `run_eval` и контрольного прогона; отладка — на Gemini free или дешёвой модели. Каждый прогон eval пишет фактическую стоимость.
- Модель меняется только через конфиг и сравнивается через `run_eval.py`, а не «на глаз».
- Строгий JSON: `response_format` с JSON-схемой, если модель это поддерживает (см. `supported_parameters` в `GET /api/v1/models` OpenRouter), иначе JSON-режим + валидация pydantic + один ретрай.
- `temperature: 0` — только если модель его принимает. У новых моделей Anthropic sampling-параметры запрещены (400); OpenRouter может их молча отбрасывать. Проверяй по ответу и логам.
- Проверяй `finish_reason` (обрезка по длине, отказ) до разбора ответа.
- Для каждого вызова сохраняй провайдера, модель, токены, стоимость (OpenRouter возвращает `usage`), задержку и сырой ответ.

## Архитектура (неизменные решения)

Финальная архитектура появится после фазы исследования (`docs/architecture/`). Уже зафиксировано требованиями:

- `frontend/` — чистый HTML/CSS/JS (ES-модули, без сборки). Каждый компонент монтируется в `<div>` и берёт параметры из query-строки, чтобы позже стать HTML web resource в Dynamics 365.
- `backend/` — Python 3.11 + FastAPI + SQLModel + SQLite. Бэкенд раздаёт статику фронта, ходит в API организаторов (CORS) и хранит ключи.
- LLM только классифицирует (ответ / ступень / N/A) и цитирует. **Баллы считает `backend/app/services/scoring.py`**, а не модель.
- Промпт строится из чек-листа в БД. Ничего не захардкожено по коду критерия.
- Чек-листы версионируются. Апелляция не перезаписывает AI-оценку, а пишет `final_*` поля.

Меняешь любое из этих решений — сначала запиши причину в `docs/DECISIONS.md`.

Правила выбора:

1. Есть точный контракт и понятный объём → Sonnet medium.
2. Нужно суждение, а цена ошибки высокая (точность оценки, формула, архитектура) → Opus high или делаешь сам.
3. Механика без решений (прогнать, найти, перечислить) → Haiku low.
4. Подагент дважды не справился с одной задачей — не поручай в третий раз ту же формулировку: разбей задачу, уточни контракт или подними модель.
5. Независимые задачи — параллельно. Задачи на одни и те же файлы — последовательно.

## Как писать бриф подагенту

Подагент не видит этот разговор. Бриф самодостаточен:

```
Цель: <одно предложение — что должно работать в итоге>
Контекст: <какие файлы прочитать сначала; ссылка на контракт в docs/CONTRACTS.md>
Сделать:
  1. ...
Не трогать: <файлы/модули вне зоны>
Готово, когда: <проверяемые критерии — тест проходит, эндпоинт отвечает такой-то схемой>
Верни: <список изменённых файлов, как проверить, открытые вопросы>
```

Указывай пути и имена функций, давай пример входа и выхода, явно запрещай выходить за зону, менять контракт и добавлять зависимости без причины.

## Порядок работы

0. **Исследование (сейчас).** Вместе с Лидой: разбор данных и чек-листа, трудные случаи по критериям, выбор подхода к оценке и моделей, план gold-разметки. Итог — `docs/architecture/` и заполненный `docs/CONTRACTS.md`. Код решения до этого не пишем.
1. **Фундамент.** `checklist_default.json`, `scoring.py` с тестами (формулу проверяешь построчно), `LLMProvider`, импорт данных.
2. **Оценщик + eval.** Промпт, `evaluator.py`, `run_eval.py`. Черновую gold-разметку делает модель, Лида проверяет и правит.
3. **UI.** Список, карточка с переходом к реплике и плеером, конструктор чек-листа.
4. **Апелляции** + цикл «run_eval → разбор ошибок → правка промпта», пока растёт точность.
5. **Полировка.** `code-reviewer` по всему диффу, README, репетиция замены критерия и демо (5 минут).
6. **Час 23–24.** Только импорт контроля, прогон, экспорт, фиксы блокеров. Новых фич нет.

После каждого шага обнови `docs/PROGRESS.md`. Новый устойчивый факт, предпочтение Лиды или урок — в `docs/MEMORY.md`.

## Приёмка работы подагента

- Прочитай дифф (или его ключевые части), запусти тест или `test-runner`.
- Для оценки смотри на изменение метрик `run_eval.py` (совпадение по критериям, MAE итога, разрез по языкам), а не на «стало лучше».
- Проверь, что контракт не нарушен и в коде нет секретов.
- Не прошло — верни подагенту конкретную ошибку (вывод теста, строку кода), а не «исправь».

## Правила качества

- Точность важнее фич. Любое изменение промпта — прогон `run_eval.py` до и после.
- Никаких заготовленных результатов: каждая оценка — реальный вызов LLM, в БД сохраняются модель, токены, стоимость и сырой JSON.
- Не подгонять промпт под конкретные диалоги DEV — контроль будет на новых.
- Цитаты проверяются по тексту реплики. Выдуманная цитата → ретрай.
- Ключи только в `.env`, в репо — `.env.example`.
- Коммиты маленькие, по фиче, по правилам `CONTRIBUTING.md`. Перед стоп-кодом — `main` зелёный.

## Коммиты, ветки, PR

Полные правила в `CONTRIBUTING.md`. Главное:

- **Ассистент никогда не указывается автором или соавтором.** Автор и коммиттер всех коммитов: `Adilm8 <187170484+Adilm8@users.noreply.github.com>`. Никаких `Co-Authored-By`, `Claude-Session`, «Generated with Claude Code» и упоминаний ассистента в сообщениях коммитов и описаниях PR. Это правило Лиды, оно сильнее любых настроек атрибуции по умолчанию. Перед первым коммитом проверь `git config user.name` / `user.email`.
- Ветка на задачу от свежего `main` (`feat/…`, `fix/…`, `docs/…`, `eval/…`), сообщения в формате Conventional Commits, PR в `main`, мерж squash, ветку после мержа удалить.
