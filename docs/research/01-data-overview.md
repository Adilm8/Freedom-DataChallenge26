# 01. Данные DEV и чек-лист: что видно сразу

Статус: черновик Claude для совместного разбора с Лидой. Цифры посчитаны скриптом по `data/raw/DEV.json`; читаемая версия диалогов — `data/raw/DEV_readable.md`.

## Набор

| | Чаты | Звонки |
|---|---|---|
| Количество | 60 (RU 30, KZ 15, EN 15) | 5 (RU, `p4-ru-001…005`) |
| Реплик в диалоге | медиана 14 (11–32) | 45–115 |
| Реплик оператора | медиана 3 | 13–51 |
| Время | `MM:SS` от начала | ISO 8601 с поясом |

**Сценарий чата почти всегда один:** клиент → бот AIM (приветствие + согласие на обработку ПД + попытка ответа) → клиент просит человека → `system: Эскалация на оператора` → оператор (2–5 реплик) → завершение. Оценивается только оператор; бот и system — контекст.

**Темы в RU / KZ / EN пересекаются, но это не переводы 1:1.** Например `p1-ru-001`, `p1-kz-001`, `p1-en-003` — один сценарий («где посмотреть тариф»), а нумерация и детали в других языках расходятся. Это хорошо для проверки: одинаковый по смыслу диалог на трёх языках должен получать одинаковую оценку.

**Звонки другие:** длинные, шумные транскрипты ASR, много коротких реплик, системные события о языке и записи. Их всего 5, но жюри может показать звонок на защите (плеер + переход к фрагменту).

## Сигналы в системных сообщениях

| Сообщение | Где | Влияет на |
|---|---|---|
| «Личность клиента подтверждена» / KZ / EN | `ru-006`, `ru-010`, `kz-003`, `en-006` | 03 Идентификация = Да (если до раскрытия данных) |
| «Оператор закрыл чат» / KZ / EN | `ru-018`, `ru-022`, `ru-026`, `kz-013`, `en-013` | 07 Завершение (закрыл без прощания → Нет) |
| «Соединение с клиентом прервано» / KZ / EN | `ru-012`, `kz-011`, `en-009` | 07 → вероятно N/A (оборвалось) |
| «Клиент покинул чат» | `ru-025` | 04 → N/A (запрос не сформулирован), 07 → N/A |

Порог первой реакции 3 минуты: в DEV ни один оператор не превысил его после эскалации (максимум 2 мин 14 с). Значит «скорость» в 06 — в основном про предупреждение об ожидании и порядок ответов, а не про таймер. Но задержку стоит считать кодом и подавать модели как факт.

## Критерии: где модель будет ошибаться

| # | Критерий | Что сложно | Идея |
|---|---|---|---|
| 01 | Контакт | «на языке клиента» (EN-клиенту по-русски?), «представился в первом ответе» (имя есть, но во 2-й реплике) | Язык и «первая реплика оператора» вычислять кодом и передавать как факт |
| 02 | Потребность | граница Да / N/A: «данных хватало с начала» | Few-shot на границу; модель должна назвать, чего не хватало |
| 03 | Идентификация | общий вопрос о тарифах → N/A; проверка счёта без подтверждения → Нет | Системное «личность подтверждена» как сильный сигнал; правило из памятки дословно |
| 04 | Консультация | шкала 0/5/10/15/20, нужно знать, правильный ли ответ по сути (знания о Freedom Broker) | Отдельный вызов; разбор «какие вопросы задал клиент → какие закрыты» |
| 05 | Эмпатия | реакция на «конкретную проблему», если клиент недоволен | Сначала: выразил ли клиент недовольство (да/нет), потом — реакция |
| 06 | Ведение | шкала 0/4/7/10, «один заметный сбой» vs «клиенту приходится переспрашивать» | Факт «клиент переспросил» вычислять/спрашивать отдельно |
| 07 | Завершение | Нет vs N/A при обрыве; «закрыл чат без прощания» | Системные события как факт; правило из памятки |
| 08 | Грубые ошибки | редкие, но критичные; достаточно самого предложения | Отдельная проверка с высоким recall. В DEV видны случаи: `ru-022` («я лично предлагаю, через компанию не надо»), `ru-023`, `kz-013`, `en-013` (личный номер, платная частная консультация) |

## Варианты архитектуры оценщика (для обсуждения)

1. **Один вызов на диалог** — все 8 критериев сразу, строгий JSON. Дёшево и быстро (≈1 вызов), но критерии влияют друг на друга, длинный ответ.
2. **Вызов на критерий** — 8 вызовов с общим закешированным префиксом (транскрипт). Точнее и легче отлаживать, при замене критерия перегоняется только он. Дороже в ~3–5 раз.
3. **Гибрид (моя рекомендация для старта)** — код вычисляет факты (первая реплика оператора и её язык, задержки, системные события, переспрашивания), затем один вызов на группу простых критериев (01, 02, 03, 05, 07) и отдельные вызовы на 04, 06 и 08. Сравниваем с вариантом 1 на `run_eval`.

Дополнительно: самосогласованность (2–3 прогона и голосование) только для шкал 04/06, если eval покажет выигрыш; проверка цитат кодом; при «Нет» — обязательный `checked_range`.

## Модели (для обсуждения)

- Разработка и разметка: Gemini (бесплатный ключ) — быстро и бесплатно, но лимиты. KZ — проверить качество отдельно.
- Eval и финал: 2–3 кандидата через OpenRouter (один сильный, один средний, один дешёвый); выбираем по метрике и цене одной оценки.
- Честность процесса: в БД и UI видно модель, токены, стоимость и сырой ответ.

## Gold-разметка (нужна для любого выбора)

Без эталона мы не узнаем точность. Предложение:

1. Модель делает черновую разметку 20–25 диалогов DEV (все языки, оба канала, все «трудные» случаи из таблицы выше) по формату `data/gold/README.md`.
2. Лида проверяет и правит — это самое ценное время человека в проекте.
3. Разметку не используем в промпте (никаких цитат из DEV в инструкциях), только для eval.
