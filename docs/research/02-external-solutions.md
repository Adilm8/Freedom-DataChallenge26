# 02. Внешние решения: как автооценку качества диалогов делают другие

Статус: исследование команды. Только веб-рисерч, без кода. Дата: 2026-11-07.

## TL;DR

1. **Наша задача почти один в один повторяет коммерческие продукты** (Amazon Connect Contact Lens, Google Quality AI, Genesys AI Scoring, Dialpad, Cresta). У всех одна схема: форма оценки из вопросов с инструкциями → LLM отвечает на каждый вопрос по транскрипту → ответ + обоснование + ссылка на реплику → человек принимает или меняет ответ. N/A исключает вопрос из расчёта и перераспределяет вес, как в нашем чек-листе.
2. **Главный урок индустрии — гибрид.** То, что лежит в структурированных данных (системные события, время, кто и когда написал первым), считает код, а не модель. Cresta: LLM «додумывала» проверку личности, которой не было; после добавления детерминированной проверки доля «пройдено» упала с 94% до 71%, то есть модель ошибалась примерно в каждом четвёртом случае. Для нас это прямо про критерии 01, 03 и 07.
3. **8 критериев в одном вызове — нормально.** Исследование по QA звонков: точность GPT-4o падает с ~0.96 при 5 вопросах в промпте до ~0.84 при 50. При 8 критериях мы в безопасной зоне, но шкалы 04/06 и флаг 08 разумно вынести отдельно.
4. **Точность поднимают:** чёткие инструкции «когда Да / Нет / N/A» на каждый критерий, рассуждение до вердикта, разбиение шкал на бинарные подвопросы, ссылки на реплики по номеру с проверкой кодом, строгий JSON.
5. **Мерить нужно согласие с человеком.** Genesys рекомендует ≥80% согласия на 20+ диалогах. Это ровно наша gold-разметка из `01-data-overview.md`.

## 1. Коммерческие продукты

| Продукт | Как устроено | Что берём |
|---|---|---|
| **Amazon Connect Contact Lens** ([docs](https://docs.aws.amazon.com/connect/latest/adminguide/generative-ai-performance-evaluations.html)) | LLM отвечает на каждый вопрос формы по его заголовку и «инструкции для оценщика». К ответу — обоснование и ссылки на точки транскрипта с переходом по времени. Если ответ не сопоставить с вариантами — N/A, вес перераспределяется. Числовые вопросы (длительность ожидания, количество перебиваний) советуют считать метриками, а не просить модель. Человек принимает или меняет ответ. Есть «язык формы»: обоснования на одном языке независимо от языка диалога. | Инструкции по каждому варианту ответа; ссылки на реплики; числа и время — кодом; обоснования на одном языке (RU) для всех трёх языков диалогов. |
| **AWS + Accenture (Bedrock)** ([блог](https://aws.amazon.com/blogs/contact-center/how-empower-scaled-contact-center-quality-assurance-with-amazon-connect-and-amazon-bedrock)) | Очередь транскриптов → Step Functions → Claude 3.5 Sonnet оценивает по 5 категориям → результат записывается в стандартный интерфейс QA. Промпты меняются без изменения системы, аналитики правят оценки. Метрик точности не публикуют. | Промпт и критерии — в конфиге, не в коде (нам это нужно для замены критерия через UI на защите). |
| **Google Quality AI** ([best practices](https://docs.cloud.google.com/contact-center/insights/docs/qai-best-practices)) | Вопросы «Did the agent…», инструкции «без пространства для интерпретации», пример диалога на каждый вариант ответа, N/A включается явно и убирает вопрос из расчёта. Типы ответов: да/нет, число/шкала, текст. Вопросы про акустику исключить. | Формат формулировок; примеры на каждый вариант (few-shot); не заставлять модель выбирать да/нет, когда возможен N/A. |
| **Genesys AI Scoring** ([best practices](https://help.genesys.cloud/articles/ai-scoring-best-practices/)) | Один вопрос — одно поведение, без нескольких условий в одном вопросе. Без субъективных формулировок («был ли вежлив?»). Подсказка должна описывать, когда выбирается каждый вариант. Проверка формы на 20+ диалогах, цель — согласие с человеком ≥80%, по каждому вопросу отдельно. | Метрика «согласие по критерию»; наши 01 и 07 составные («поздоровался **и** представился», «итог **или** помощь **и** прощание») — их стоит разложить на подпункты внутри промпта. |
| **Cresta** ([блог](https://cresta.com/blog/how-cresta-grades-its-agents-evaluators-in-an-llm-world)) | Каждое требование — бинарный оценщик. LLM-судья — для смысловых суждений, детерминированные проверки — для всего, что есть в данных (вызовы инструментов, действия). Калибровка: люди соглашаются / не соглашаются с вердиктами, формулировки уточняют до стабильности. Предупреждают: перегиб в сторону LLM-судьи дорог и ненадёжен. | Гибрид «факты кодом + суждения моделью»; цикл калибровки по gold-разметке. |

Вывод: чек-лист организаторов (веса, N/A с перераспределением, грубые ошибки отдельно, обоснование + фрагмент, апелляция) — это та же модель данных, что у Contact Lens и Quality AI. Изобретать ничего не нужно, нужно аккуратно повторить проверенную схему.

## 2. Исследования

| Работа | Результат | Значение для нас |
|---|---|---|
| **Multi-question answering на транскриптах звонков** ([arXiv 2509.21732](https://arxiv.org/html/2509.21732v1)) | 2 800 ASR-транскриптов, да/нет-вопросы, ответ + индекс подтверждающей реплики. GPT-4o: точность суждения 0.96 при 5 вопросах → 0.84 при 50; точность «навигации» (верная реплика) 0.90 → 0.75. GPT-4o > GPT-4o-mini > Gemini-1.5-flash. Результат меньше зависит от модели. |

KZ-диалоги проверить в eval отдельно; для KZ может понадобиться более сильная модель, чем для RU/EN. |

## 3. Практики LLM-as-judge (сводка)

Из гайдов ([Galileo](https://galileo.ai/blog/tricks-to-improve-llm-as-a-judge), [Arize](https://arize.com/docs/ax/concepts/evaluators/evaluator-best-practices)) и документации выше:

- **Бинарные вердикты лучше числовых шкал**; шкалу — через подвопросы.
- **Рассуждение до вердикта**: в JSON-схеме поле `reasoning` / `evidence` идёт раньше `answer`.
- **Few-shot из реальных расхождений** модели с человеком (у нас — из расхождений с gold, но не цитатами из тех же DEV-диалогов, которые используем для eval).
- **Структурированный вывод** вместо парсинга текста.
- **Голосование нескольких прогонов / судей** — только там, где eval покажет нестабильность (шкалы).
- **Цикл калибровки с человеком** — у нас это gold-разметка и апелляции.

Технически на OpenRouter ([structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs.md)): `response_format: {type: "json_schema", strict: true}`, плюс `provider.require_parameters: true`, чтобы запрос не ушёл к провайдеру без поддержки схемы. Поддержка зависит от провайдера, а не только от модели; есть плагин response-healing для починки JSON. Всё равно валидируем Pydantic и при ошибке повторяем.

## 4. Классическая speech analytics (без LLM)

Старые системы (поиск ключевых фраз, «скрипт-комплаенс» по расстоянию между ключевыми словами, словари) хороши для жёстких формулировок и дёшевы, но плохо переносят перефразирование и три языка. Для нас имеет смысл как **дешёвый страховочный слой**, а не основа:

- 08 «Грубые ошибки»: регулярки на «лично», «мой номер», «переведите мне», «в обход», KZ/EN-аналоги → флаг «проверить» поднимает recall, финальное решение за LLM.
- 01: приветствие и имя в первой реплике оператора — словарь приветствий на 3 языках как подсказка модели.

## 5. Что из этого применимо к нам за один день

**Берём (дёшево, сильный эффект):**

1. **Слой фактов кодом** перед LLM: нумерация реплик; первая реплика оператора и её язык; язык клиента; задержка первой реакции после эскалации и паузы между репликами; системные события (личность подтверждена, оператор закрыл чат, соединение прервано, клиент ушёл) с позициями. Подаём модели как «факты», а в UI показываем как подсказки.
2. **Чек-лист как конфиг** (JSON в БД): на каждый критерий — формулировка, тип, вес, N/A, шкала и **инструкции «Да когда… / Нет когда… / N/A когда…»** из памятки. Промпт собирается из конфига → замена критерия на защите без правки кода.
3. **Строгая схема ответа** на критерий: `reasoning` → `answer` → `evidence: [{utterance_idx, quote}]` → `checked_range` (для «Нет») → `na_reason` (для N/A).
4. **Проверка кодом**: ответ из разрешённых вариантов, N/A только где разрешён, индекс реплики существует и это реплика оператора/клиента/system по смыслу, цитата — подстрока реплики (нечёткое сравнение). При провале — один повтор с указанием ошибки.
5. **Расчёт баллов только кодом** по правилам чек-листа (вес, перераспределение N/A, округление, флаг 08). Модель цифры итога не считает.
6. **Gold + метрика согласия по критерию** (цель ≥80%, как у Genesys), отдельно по RU/KZ/EN.
7. **Апелляция = человеческий override**, как во всех продуктах: храним исходную оценку модели, решение проверяющего с причиной и финальную; итог пересчитывается кодом.

**Берём, если останется время:**

- Подвопросы для шкал 04/06 (CheckEval) с маппингом в ступень кодом.
- 2–3 прогона и голосование для 04/06.
- Регулярки-страховка для 08.
- Второй, более сильный судья только для KZ или только для спорных критериев.

**Не берём:**

- Fine-tuning маленьких моделей (в статьях даёт хороший результат, но нет данных и времени).
- RAG по базе знаний Freedom: нет базы. Для 04 опираемся на здравый смысл модели и на то, что сказал бот/оператор.
- Оценку тона и дикции по аудио: транскрипты достаточно, аудио только для плеера.
- Очереди, Step Functions и прочую инфраструктуру: 65 + 10 диалогов прогоняются синхронно батчем.

## 6. Набросок архитектуры для обсуждения

```
API организаторов ──► fetch + normalize (индексы реплик, роли, время)
                             │
                             ▼
                  facts (код): язык, первая реплика оператора,
                  задержки, системные события, флаги-регулярки 08
                             │
        чек-лист (JSON) ──►  ▼
                  judge (LLM, OpenRouter / Gemini):
                  вызов A — 01,02,03,05,07 ; вызов B — 04,06 ; вызов C — 08
                  строгий JSON: reasoning → answer → evidence[idx, quote]
                             │
                             ▼
                  validate (код): варианты, N/A, цитаты, повтор при ошибке
                             │
                             ▼
                  score (код): веса, перераспределение N/A, округление, флаг 08
                             │
                             ▼
                  SQLite: evaluations / appeals / decisions / checklist versions
                             │
                             ▼
                  UI (HTML/CSS/JS): список → карточка → клик по доказательству
                  → реплика / время в плеере → апелляция → решение → новый итог
```

Стартовать можно с одного вызова на диалог (все критерии), а разбиение A/B/C включить, если eval покажет выигрыш. Замена критерия на защите: новая версия чек-листа → перегоняем только изменённый критерий (если вызов на группу — только его группу).

## 7. Вопросы к Лиде для обсуждения архитектуры

1. Один вызов на диалог на старте и разбиение по группам после eval — согласна?
2. Язык обоснований: всегда русский (удобнее жюри) или язык диалога?
3. Какую модель берём как основную для eval: есть ли предпочтение (GPT-4o-класс / Gemini Flash / Claude через OpenRouter), и какой бюджет на OpenRouter?
4. Хранение: SQLite + FastAPI (уже в каркасе) — ок?
5. Готова ли ты разметить 20–25 диалогов gold (это главный способ доказать жюри точность)?
