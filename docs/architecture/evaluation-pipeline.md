# Конвейер оценки (ядро)

> Статус: черновик v0.2 · Обновлено: 2026-11-07 · Владелец: Claude (+ `llm-eval-engineer`) · Утверждает: Лида
> От этого документа зависит главный критерий жюри. Любое изменение здесь — `run_eval.py` до и после.

```
conversation ─► normalize ─► facts ─► partition(strategy) ─► judge × N (параллельно)
                                                                  │
                     scoring ◄── guards ◄── validator (1 ретрай) ◄┘
```

## 1. Нормализация (`services/normalize.py`)

- `msg_id = "m<idx>"` по исходному порядку, начиная с `m0`. Исходные `timestamp`, `speaker`, `text` не меняем (FR-DATA-03).
- `t_sec`: чат — `MM:SS` или `H:MM:SS` в секунды; звонок — ISO 8601 минус время первой реплики.
- Роли как есть: `client`, `operator`, `bot`, `system`; неизвестная роль сохраняется и считается контекстом.
- **Сегменты звонка** по системным событиям: удержание клиента, консультация с другим агентом (в `p4-ru-002` оператор говорит с коллегой, пока клиент на удержании), пауза и возобновление записи, смена языка. Реплики оператора внутри консультации помечаются `internal: true`: они контекст, а не общение с клиентом.
- `audio_offset_sec` для звонков: время от начала записи с вычетом пауз записи. Если события записи нет, считаем от первой реплики. В карточке есть ручная поправка смещения на случай расхождения (FR-CARD-04).

## 2. Факты (`services/facts/`)

Факты считает код. Модель получает их отдельным блоком «Факты, вычисленные системой», а UI показывает их как подсказки. Факт — это `{value, msg_ids, note}`. Каждый извлекатель — функция в реестре; новый факт = новая функция, остальной код не меняется. Словари фраз на трёх языках — `data/config/lexicons.json` и `system_events.json`, их можно дополнять без правки кода.

| Факт | Как считается | Помогает критериям (по умолчанию) |
|---|---|---|
| `escalation_at` | первое системное «Эскалация / Chat transferred / жіберілді»; если нет — первая реплика оператора | 01, 06 |
| `first_operator_msg` | первая реплика оператора после эскалации, не `internal` | 01 |
| `first_response_delay_sec` | `t_sec(first_operator_msg) − t_sec(escalation_at)` и флаг `> 180 с` (порог из настроек чек-листа) | 06 |
| `client_language` | поле `language` записи, сверка по алфавиту и словарю (казахские буквы `әғқңөұүһі`) | 01 |
| `operator_first_msg_language` | та же эвристика по первой реплике оператора | 01 |
| `greeting_in_first_msg`, `intro_in_first_msg` | словарь приветствий и шаблоны представления («меня зовут», «я <Имя>», «I'm», «менің атым», «мен <Имя>») | 01 |
| `system_events[]` | классификация системных сообщений: `identity_verified`, `operator_closed`, `connection_lost`, `client_left`, `client_ended`, `hold_start/end`, `consult_start/end`, `recording_paused/resumed`, `language_changed` | 03, 04, 07 |
| `identity_verified_at` | первое `identity_verified` | 03 |
| `long_gaps[]` | паузы оператора после реплики клиента дольше порога; было ли перед паузой предупреждение («минуту», «ожидайте», «please wait», «күте тұрыңыз») | 06 |
| `last_operator_msg`, `farewell_in_last_msg` | последняя реплика оператора и словарь прощаний | 07 |
| `ended_by` | кто закончил: клиент ушёл, связь прервалась, оператор закрыл чат, обычное завершение | 04, 07 |
| `risk_terms[]` | словарь рискованных фраз: «на мою карту», «лично», «мой номер», «в обход», «платно», «personal», «my card», «жеке», «ақылы» | 08 |
| `operator_turns`, `client_turns` | счётчики | все |

Факты — подсказка, а не вердикт: решение за моделью, если в чек-листе для критерия не включено правило-страховка (раздел 6). Так замена любого критерия через UI ничего не ломает: факты общие и не привязаны к коду критерия.

## 3. Промпт (`services/prompt_builder.py`, `backend/app/prompts/`)

Порядок частей выбран так, чтобы общий для всех вызовов префикс шёл первым и кешировался провайдером (OpenAI, Gemini и DeepSeek кешируют префикс сами; Anthropic через OpenRouter — с `cache_control`):

1. **system** (`system.md`) — роль «оценщик качества работы оператора»; общие правила из памятки почти дословно: оценивается только оператор, бот и system — контекст; «Нет» против N/A; N/A только где разрешён и выполнено условие; доказательство — конкретная реплика; для пропуска — место, где действие ожидалось; язык обоснований = `settings.output_language`, цитаты — на языке оригинала; не додумывать то, чего нет в тексте. Отдельно (FR-EVAL-16): каждое утверждение обоснования опирается на реплику или факт; если данных для вывода не хватает, так и написать, поставить `confidence: low` и не достраивать недостающее; утверждения клиента или оператора, которые нельзя проверить по тексту, не считать ни верными, ни ложными.
   **Правила канала** (`channel_voice.md`, сразу после system) — только для `voice call` (FR-EVAL-17): это расшифровка устной речи; оговорки, повторы, слова-паразиты, ошибки распознавания и перекрытия не считаются ошибкой оператора; грамотность по расшифровке не оценивается; удержание и паузы — по фактам сегментов. Шаблон выбирается по каналу диалога, а не по коду критерия.
2. **Факты** — список из раздела 2 с `msg_id`.
3. **Транскрипт** (`transcript.md`) — по строке на реплику: `[m9 | 01:15 | operator] Здравствуйте! Меня зовут Алина…`. Внутренние реплики звонка помечены `operator·internal`.
4. **Критерии этого вызова** (`criterion.md`) — из данных чек-листа: код, название, секция, формулировка, тип, «Да, когда… / Нет, когда…», условие N/A (если разрешён), ступени шкалы с описаниями, подсказка оценщику (`guidance`). Если у критерия есть `context_refs` (по умолчанию у 04 — `data/knowledge/freedom_broker_kb.md`), справка подставляется сюда с пометкой «подсказка, а не эталон» ([ADR-011](../decisions/ADR-011-product-knowledge.md)).
5. **Формат ответа** (`output_rules.md`) — коротко; сама схема уходит в `response_format`.

Тексты лежат в `.md`-шаблонах с плейсхолдерами (`string.Template`, без новых зависимостей). У шаблонов есть `PROMPT_VERSION`, он пишется в каждую оценку.

Чего в промпте нет и не будет: цитат и примеров из DEV-диалогов (контроль на новых, NFR-05). Если понадобятся few-shot примеры, пишем свои синтетические и держим их в `prompts/examples/`.

## 4. Схема ответа

Генерируется из чек-листа под каждый вызов: для каждого критерия вызова — объект со своим `enum` ответов. Модель физически не может вернуть «N/A» там, где он запрещён, или ступень, которой нет на шкале.

```json
{
  "results": {
    "01": {
      "reasoning": "≤ 3 предложения",
      "answer": "yes | no",
      "confidence": "high",
      "evidence": [{"msg_id": "m9", "quote": "Здравствуйте! Меня зовут Алина."}],
      "checked_range": null,
      "na_reason": null,
      "advice": null
    },
    "04": { "reasoning": "...", "answer": "0 | 5 | 10 | 15 | 20 | na", "confidence": "medium", "evidence": [], "checked_range": {"from": "m9", "to": "m11"}, "na_reason": null,
            "advice": "Назвать срок зачисления и куда смотреть статус." }
  },
  "overview": { "summary": "Клиент не видит пополнение счёта; оператор проверил платёж и назвал срок.", "topic": "Пополнение счёта", "resolved": "yes" }
}
```

`confidence`, `advice` (FR-EVAL-18) и `overview` (FR-EVAL-19, только в первом вызове) ничего не стоят сверх уже идущих вызовов и на баллы не влияют.

`reasoning` идёт раньше `answer` (модель сначала рассуждает). Точная схема — `CONTRACTS.md` §2. Строгий режим: `response_format: {type: "json_schema", strict: true}` и `provider.require_parameters: true` на OpenRouter; если модель не поддерживает — JSON-режим + Pydantic + ретрай.

## 5. Стратегии вызовов ([ADR-002](../decisions/ADR-002-call-strategy.md))

Стратегия — это только способ разбить критерии на вызовы. Код один, меняется параметр.

| Стратегия | Вызовов на диалог | Плюсы | Минусы |
|---|---|---|---|
| `single` | 1 | дёшево, быстро, удобно для отладки на Gemini free | критерии влияют друг на друга, длинный ответ |
| `grouped` | по группам из `criterion.group` или настройки (например 01-02-03-05-07 / 04-06 / 08) | компромисс | группы надо подбирать |
| `per_criterion` | по числу критериев (8) | фокус, изоляция ошибок, легко перегнать один критерий, лучше для нового критерия на защите | дороже в 3–6 раз (смягчается кешем префикса) |

**По умолчанию — `grouped`** (решение Лиды, вариант 3 из `research/01`): вызов A — 01, 02, 03, 05, 07; отдельные вызовы — 04, 06, 08. Итого 4 вызова на диалог. Группа — поле `group` критерия в чек-листе; критерий без группы (например, новый, добавленный на защите) получает свой вызов. Реализуем все три стратегии сразу (это одна функция `partition`), на gold сравниваем `grouped` с `single` и `per_criterion` и меняем умолчание, только если метрика это покажет.

Вызовы одного диалога идут параллельно, общий лимит параллельности на провайдера — настройка (у Gemini free низкий RPM).

## 6. Проверка (`services/validator.py`) и страховки (`services/guards.py`)

| # | Проверка | При ошибке |
|---|---|---|
| V1 | JSON разобран и соответствует схеме | ретрай |
| V2 | Есть результат по каждому критерию вызова | ретрай недостающих |
| V3 | `answer` из разрешённых для критерия; `na` только где `na_allowed` | ретрай |
| V4 | Каждый `msg_id` существует | ретрай |
| V5 | `quote` — подстрока текста этой реплики (без учёта регистра, пробелов, кавычек; нечётко ≥ 0.85 у чатов и ≥ 0.75 у звонков, `settings.quote_threshold`) | ретрай; после — убрать цитату, пометить |
| V6 | `answer = no` → есть `checked_range` или доказательство | пометка |
| V7 | `answer = na` → есть `na_reason` | пометка |
| V8 | Доказательство по критерию работы оператора ссылается на реплику оператора, клиента или system в нужном диапазоне, а не только на бота | пометка |
| V9 | `finish_reason` не `length` и не отказ | ретрай с большим `max_tokens` |
| V10 | `confidence = low` | пометка «требует проверки» и строка в очереди (FR-UX-02) |
| V11 | `advice` при полном балле | убрать без ретрая |

Ретрай один: те же сообщения + ответ модели + список ошибок. Если и он не прошёл — сохраняем лучший вариант с `needs_review: true` и предупреждениями (FR-EVAL-04, FR-RES-05). Прогон не падает.

**Страховки (C, FR-EVAL-12).** У критерия в чек-листе может быть список правил вида «если факты X, ответ должен быть из множества Y; действие: `flag` или `override`». По умолчанию только `flag`: противоречие подсвечивается в UI и в eval. `override` включаем для критерия, только если eval покажет, что правило точнее модели. Примеры для чек-листа по умолчанию (это данные, не код):

- 07: `ended_by ∈ {client_left, connection_lost}` до прощания оператора → ожидаем `na`.
- 01: в первой реплике оператора нет ни приветствия, ни представления → ожидаем `no`.
- 03: модель ответила `yes`, а в чате нет `identity_verified` → `flag` (в звонках идентификация бывает голосом, поэтому не `override`).

## 7. Баллы (`services/scoring.py`)

Чистая функция по правилам чек-листа (FR-SCORE-01…08, [ADR-006](../decisions/ADR-006-scoring-rules.md)):

- `binary`: `yes` → вес, `no` → 0; `scale`: `вес × ступень / max(ступеней)`; `flag`: баллов нет, в список флагов.
- `na` исключает критерий из применимого веса.
- Итог = `Σ баллов / Σ применимых весов × 100`, округление до 2 знаков **половина вверх** (`Decimal`, а не `round()`).
- Секции: баллы, применимый вес, процент.
- В UI у критерия показываем «баллы / вес» и вклад в итог после перераспределения.
- Контрольный тест — пример из чек-листа: 04 = N/A, 06 = 7, остальное «Да» → **94.38**.

## 8. Трудные места и чем закрываем

| Критерий | Где модель ошибается | Чем закрываем |
|---|---|---|
| 01 | «на языке клиента», «представился в первом ответе» | факты `first_operator_msg`, язык, приветствие, представление; страховка `flag` |
| 02 | граница «Да» / N/A («данных хватало с начала») | инструкция «назови, чего не хватало для ответа»; синтетический few-shot, если eval покажет |
| 03 | N/A для общего вопроса, «Нет» при раскрытии данных без проверки (`en-014`, `kz-015`) | правило памятки дословно; факт `identity_verified_at`; модель называет реплику раскрытия, код сверяет порядок |
| 04 | шкала 0–20, знание сути продукта | разбор «какие вопросы задал клиент → какие закрыты»; при нестабильности — подвопросы и медиана нескольких прогонов (C) |
| 05 | «если клиент выразил недовольство» | сначала: было ли недовольство (реплика), потом: реакция на конкретную проблему |
| 06 | «один сбой» против «приходится переспрашивать» | факт `long_gaps` и предупреждение; модель называет реплику переспроса |
| 07 | «Нет» против N/A при обрыве; «закрыл без прощания» | факты `ended_by`, `farewell_in_last_msg`; страховка для N/A |
| Неполные данные | обрыв, клиент ушёл, только бот, нет реплик оператора | факты `ended_by`, `first_operator_msg`; правило «не достраивать»; N/A, где разрешён, иначе ответ по правилу с `confidence: low` и пометкой; нет применимых критериев → итог `null` |
| Непроверяемые утверждения | модель «знает», верен ли ответ о продукте | справка для 04 только как подсказка; без опоры — `confidence: low`, ошибка не придумывается |
| Звонки | ошибки распознавания принимают за ошибки оператора, цитаты не совпадают | правила канала `channel_voice.md`, мягкий порог цитат |
| 08 | редкие, но критичные; достаточно предложения | отдельный критерий-флаг; `risk_terms` как подсказка для recall; цель recall 100% |

## 9. Стоимость и время (оценка до bake-off)

Чат: ~2–3 тыс. токенов префикса (правила + факты + транскрипт) и ~0.3–0.6 тыс. на критерий. `grouped` ≈ 4 вызова ≈ 12 тыс. входных и 2 тыс. выходных токенов на чат; `per_criterion` ≈ 8 вызовов ≈ 25 тыс. и 3 тыс.; с кешем префикса заметно дешевле. Звонок в 3–5 раз больше. Точную цену одной оценки пишет каждый `llm_call` (OpenRouter возвращает `usage` и стоимость), сводку — `run_eval.py`; итоговая цифра идёт в README (FR-OPS-03).

## 10. Инкрементальная переоценка (`services/reuse.py`, FR-CHK-10)

- У каждого критерия есть `criterion_hash` — хеш полей, которые попадают в промпт (название, тип, формулировка, «Да, когда / Нет, когда», N/A, шкала, подсказка, `context_refs`), плюс `PROMPT_VERSION` и модель. Вес, секция и порядок в хеш не входят.
- При `reuse: auto` для каждого диалога берём последнюю оценку той же моделью. Критерий с тем же хешем переиспользуем, остальные оцениваем вызовами по стратегии (новый критерий без группы — свой вызов). `overview` тоже переиспользуется.
- Смена только весов, секций или политики → ноль вызовов LLM, итоги считает `scoring` за секунды.
- Переиспользованный результат помечен `reused_from_evaluation_id`, в карточке видно «ответ из оценки #…». «Оценить повторно» и контрольный прогон идут с `reuse: none`.

## 11. Воспроизводимость (FR-EVAL-20, NFR-14)

`temperature: 0` и `seed`, если модель их принимает; фактические параметры пишутся в `llm_call.request` и `evaluation.params`. Версия чек-листа, промпта, модель и стратегия сохранены у каждой оценки, поэтому любой результат можно повторить. Стабильность меряет `run_eval.py --repeat 2`, результат — на экране качества.
